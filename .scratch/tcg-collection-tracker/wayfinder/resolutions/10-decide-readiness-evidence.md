# Resolution — Evidence required for implementation readiness

**Deployment amendment:** [ADR 0002](../../../../docs/adr/0002-defer-deployment-provider-selection.md) defers the provider-specific quotas and named service usage below. The launch fixture, privacy, recovery, performance, and cost proof remain required for the eventual providers.

The owner confirmed the two-gate evidence contract below.

## Gates and evidence matrix

The current `spec.md` and ten implementation tickets describe the superseded AWS/DynamoDB and English/Japanese approach. The revised handoff must reconcile every approved Wayfinder resolution, remove contradictory old requirements, and link each new acceptance criterion to an implementation ticket. The owner approved two separate gates: an **implementation handoff** that is complete enough to build, and a **launch** gate that requires results from the built application and live services. Owner-only deployment and later public signup have distinct launch prerequisites under the hosting resolution.

| Area | Handoff evidence to specify | Launch evidence to collect |
| --- | --- | --- |
| Traceability and contracts | A requirement-to-ticket matrix for all approved decisions; runtime-validated API shapes, stable error codes, domain glossary, data invariants, schema/migration plan, and a dependency-ordered vertical-slice ticket set. Explicitly mark English-only, leaf-only Locations, PostgreSQL, manual catalog pulls, and owner-only first release as replacements for the old spec. | CI results against the exact release commit and a review of any deviations from the approved contract. |
| Catalog and overrides | Fixtures for a complete English import, variant ambiguity, missing image, Basic Energy uncertainty, tombstoned owned Editions, source rename, duplicate manual report, later TCGdex match, and cursor invalidation. Specify owner review and fresh-code cases. | Run one complete owner-triggered import; prove atomic promotion and rollback under injected failure, immediate approved-manual-entry search, image/placeholder behavior, and correct last-pull timestamp. |
| Inventory and Decks | Worked scenarios for `Unsorted` onboarding, two stocked-leaf conversions, 12-level/cycle/sibling-name rules, Add/Move/Removal, stale two-tab edits, 25,000-Edition atomic transfer, idempotent retry, five ten-minute Undo actions, derived totals, and Deck checks at 59/60/61 copies plus four-copy and uncertain Basic Energy cases. | Run contract/browser tests through public interfaces and a real PostgreSQL integration suite; inject a transfer failure and verify no partial Holdings; check physical quantity conservation and no negative balances. Verify keyboard/touch controls and failure recovery from the approved prototype. |
| Authentication and privacy | Threat cases for cross-owner IDs, uniform not-found responses, OTP guessing/rate limits, 30-day rolling sessions, CSRF, open redirects, owner endpoint authorization, fresh-code approval, public-token guessing, escaped public content, and log redaction. Define allowed and forbidden Published Deck fields. | Test real owner OTP delivery in owner-only mode; test a separate real recipient only after sender-domain verification and before public signup. Assert serialized public responses and R2 projections exclude every private field. Confirm revoked URLs and Listed/Unlisted discovery behavior on the next request. |
| Scale, latency, and cost | A reproducible fixture/workload specification: 1,000 registered accounts, 200 monthly active users, one 25,000-Holding collector, complete English catalog plus indexes and auth, five worst-case Undo payloads, and 10,000 anonymous Published Deck views/month. Define cold/warm measurements and provider usage/cost arithmetic, including the 350 MB Neon warning gate and the agreed under-$10 monthly idle target excluding domain and separately itemized request/email use. | At that fixture size, 95% of warmed Collection/Location page loads complete within two seconds and ordinary inventory actions within five seconds; measure cold starts separately. An extreme 25,000-Edition Move completes within two minutes from pressing Move, including selection staging, with visible progress and no partial inventory change. Two minutes is a maximum, not the expected duration or a product-level selection limit; record actual timing and optimize slow operations. Report query plans, response distributions, transaction duration, database bytes, Neon compute/egress, Workers requests/logs, R2 operations, Resend sends, and Actions usage. Prove public views do not wake PostgreSQL. Optimize or upgrade a constrained component if a required limit is exceeded. |
| Release and recovery | Specify CI checks, manual release workflow, migration/rollback sequence, daily backup, monthly disposable restore, hourly backup-age watchdog, alert paths, 70% quota warnings, and runbooks. | Deploy the exact CI-passing main commit through the manual gate; smoke-test auth/API/static assets; restore a real backup into a disposable database and compare expected row counts and key invariants; prove watchdog/alert and rollback paths with safe failure drills. |

Automated tests should check observable results rather than private helper calls. Every launch proof should record the fixture and environment, command or reproducible procedure, expected and actual result, date, and a private location for sanitized artifacts. Privacy, data integrity, atomicity, backup recovery, authorization, and agreed capacity/performance limits block launch; other deviations need a documented decision rather than silent acceptance.

Before public signup, the owner personally walks through search, Add, Move, Undo, Deck checks, and publish/revoke on the owner-only deployment using desktop and mobile. This complements, but does not replace, automated checks. Public signup also remains blocked until the verified-domain real-recipient OTP test succeeds.
