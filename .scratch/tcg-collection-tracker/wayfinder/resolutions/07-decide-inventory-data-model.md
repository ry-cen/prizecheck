# Resolution — Relational transactional inventory model

**Deployment amendment:** [ADR 0002](../../../../docs/adr/0002-defer-deployment-provider-selection.md) defers the named Neon capacity gate below; measure the same workload against the chosen PostgreSQL provider.

The owner confirmed this contract. The [interaction contract](08-decide-core-interaction-contract.md) defines the visible workflows; this resolution specifies their storage, concurrency, and failure behavior.

## Confirmed product decisions

- Reparenting an existing Location beneath a stocked ordinary storage leaf offers an atomic conversion: create an `Unsorted` child for the destination's existing Holdings, move those Holdings into it, and place the reparented Location beneath the destination. The owner may cancel instead. Any failure leaves the original tree and Holdings intact.
- Location trees have a maximum depth of 12 nodes, counting the top-level Location as level one and including a Deck or ordinary storage leaf at the final level.
- Sibling Location names are unique after trimming surrounding whitespace and comparing without case; duplicate names in different branches are allowed.
- Collection totals are derived from current Holdings with indexed aggregate queries rather than stored in a separate summary table. Query performance is a readiness measurement against the 25,000-Holding fixture.
- Undo covers the last five Moves or Inventory Removals in newest-first order. Each ephemeral inverse-operation record becomes unusable exactly 10 minutes after its action; the next inventory action or daily maintenance physically deletes expired records. There is no permanent movement/audit history. An Undo remains all-or-nothing and fails without overwriting intervening incompatible changes. Test worst-case storage with 25,000-Edition transfers against the Neon storage gate.
- Collection and Location listing cursors bind the owner's inventory revision. If inventory changes between pages, the next page returns a refresh notice and the UI restarts at page one rather than mixing revisions.

## Implementation contract

### Relational state and constraints

- `inventory_owner(user_id, revision)` has one row per application user. The account-creation database transaction creates this row and the initial ordinary `Unsorted` root storage leaf together. Use a database trigger on the Better Auth user insertion if its adapter cannot join an application transaction; signup must not leave an account without `Unsorted`.
- `location(id, owner_id, parent_id, kind, name, name_key, depth, version)` is an adjacency tree. `kind` is only `ordinary` or `deck`; an ordinary Location's organizational-versus-leaf role is derived from whether it has children. `deck_detail(location_id, owner_id, declared_format, ...)` contains Deck-only metadata. IDs are immutable opaque application IDs, not paths or names.
- A composite `(owner_id, parent_id)` foreign key references a parent owned by the same user. The root parent is null. Distinct partial unique indexes enforce normalized `name_key` among roots and among children of each parent. The application trims names, rejects empty/control-character names, limits display names to 120 characters, and computes `name_key` by Unicode normalization plus case folding. Names elsewhere in the tree may repeat.
- `holding(owner_id, location_id, edition_id, quantity, version)` has one row per Card Edition and storage leaf, with a unique key on `(owner_id, location_id, edition_id)`, a positive 64-bit quantity check, an owned-Location foreign key, and a Card Edition foreign key. A zero result deletes the row. The `version` comes from a monotonically increasing owner revision so deleting and later recreating a Holding does not reuse an old version. API quantities are decimal strings when needed to avoid JavaScript integer loss.
- `selection_manifest(id, owner_id, source_location_id, destination_location_id, action, state, expires_at, request_key)` and `selection_item(manifest_id, edition_id, quantity, expected_source_version)` hold one pending bulk Move or Inventory Removal. `undo_action(id, owner_id, action, inverse_payload, created_at, expires_at)` holds only the short-lived inverse details. `mutation_request(owner_id, request_key, command_digest, outcome, expires_at)` keeps a command fingerprint and minimal applied result for 24 hours so a lost HTTP response cannot cause a second mutation; reuse of a key for a different command is rejected. It stores no Edition, quantity, Location, or inverse-operation details. These are operational records, not a permanent movement ledger; expired manifests and Undo payloads are excluded from logical backups.
- Database foreign keys and checks enforce ownership, uniqueness, positive quantity, and valid references. Deferred constraint triggers enforce cross-table rules at commit: Decks have no children, organizational Locations have no Holdings, and children never have a Deck parent. All application mutations acquire the owner's `inventory_owner` row lock first, then validate the tree/leaf rules; the triggers guard against a bypassing write. A recursive ancestor/descendant query rejects cycles and any resulting depth above 12. PostgreSQL supports recursive queries and row locks for these checks ([recursive queries](https://www.postgresql.org/docs/current/queries-with.html), [row locks](https://www.postgresql.org/docs/current/explicit-locking.html)).
- Tombstoned Card Editions remain referenced by existing Holdings and may be moved or removed. New Add commands cannot select a tombstoned Edition. Deleting a Location is non-recursive and requires no children or Holdings; foreign keys restrict accidental orphaning.

### Transactions and concurrency

- Every Location, Deck, Holding, or Undo mutation takes the `inventory_owner` lock, so inventory commands by one owner serialize while different owners do not block each other on that lock. Each committed inventory mutation increments `inventory_owner.revision`; temporary manifest uploads and cleanup do not. Client-supplied owner IDs are ignored; the authenticated application user ID determines the tenant. Queries and updates always scope by owner ID, and cross-owner resource IDs return the same not-found result as nonexistent IDs.
- Commands carry an idempotency key. A committed key returns its stored outcome on retry within 24 hours; clients retry an uncertain response with that same key during this window, while an unknown key starts a new command. Location rename/reparent/delete commands require the displayed Location version. Move and Inventory Removal require expected source-Holding versions for every selected Edition; if any source changed, the whole command fails and retains the UI selection. Add is an atomic increment under the owner lock, so it does not require a previously read Holding version. Destination quantities increment under the same lock and do not require a stale destination version.
- Add validates an owned ordinary or Deck storage leaf, active Edition, and positive quantity, then upserts a single Holding. Inventory Removal validates every selected source quantity, subtracts or deletes rows, and creates an Undo record in the same transaction. The same batched selection-manifest protocol used for Move supports a large Removal. Collection totals change only because Holdings change; no separate summary needs maintenance.
- A Move starts from one source storage leaf and ends at one distinct destination storage leaf. Selection can contain any number of Card Editions owned in that source. The browser uploads its selection to a server-owned manifest in bounded HTTP batches; one live manifest per user, unique Edition rows, positive quantities, source versions, and a one-hour staging expiry prevent duplicate or abandoned payloads. There is **no product-level Edition count limit**. The final commit locks the owner, verifies manifest completeness, source versions and quantities, destination leaf/ownership, and idempotency; then one PostgreSQL transaction performs set-based source decrements/deletes and destination upserts, records the inverse Undo data, and advances the revision. Failure or disconnection leaves no partial transfer; retrying the commit key reports the committed result or safely completes it. The manifest is deleted after success or expiry.
- Undo stores at most the five most recent Move or Inventory Removal inverse payloads per owner as compact PostgreSQL data, each with an exact ten-minute `expires_at`. Only the newest non-expired entry is eligible, then the next becomes eligible after it is undone or explicitly dismissed. A Move inverse transfers its quantities back; a Removal inverse re-adds them to the original leaf. Under the owner lock, Undo checks that all involved Locations still exist as owned storage leaves and that every inverse subtraction is available. If not, it changes nothing and returns a conflict; the user may dismiss that entry to reach an older one. It does not overwrite an intervening Add or compatible quantity change; Holdings are fungible by Card Edition. Expired entries are unusable immediately and are physically cleared on the next inventory action or by the daily backup-maintenance job, avoiding a database-waking cleanup timer. There is no permanent movement history.
- Creating a first child beneath a stocked leaf follows the approved guided conversion. Reparenting a Location beneath a stocked leaf uses the newly agreed `Unsorted` conversion, atomically moving the destination's Holdings to that child and inserting the reparented subtree. Each structural command checks owner, parent kind, cycle, sibling name conflict, and depth of the entire moved subtree; updates all affected depths and Location versions in one transaction. A Deck remains a leaf, and reparenting cannot put any Location beneath a Deck. Deleting or moving the final child makes the old parent an empty storage leaf.

### Reads and pagination

- Index `holding(owner_id, location_id, edition_id)` for leaf contents and transactional selection; index `holding(owner_id, edition_id, location_id)` for Collection totals and per-Edition Location distribution. Index `location(owner_id, parent_id, name_key, id)` for tree children, plus Deck lookup by owner and kind. Use `SUM(quantity)` grouped by Edition for Collection and recursive descendant queries for organizational Location rollups; no Collection summary table or recursive stored counts. Measure these queries with the 25,000-Holding fixture.
- Location grid, Collection, and Deck indexes use deterministic keyset pagination, not offset: sort by the relevant catalog/name key and immutable ID, with a default 48 Holdings per grid page and 30 Collection/Deck entries per list page. The opaque cursor binds owner, normalized filters, sort tuple, `inventory_owner.revision`, and the active catalog revision when catalog fields affect ordering. A revision change returns `INVENTORY_CHANGED` or `CATALOG_CHANGED`; the UI explains the refresh and starts at page one. The cursor is validated and cannot be reused for a different owner or filter. PostgreSQL notes that offsets compute skipped rows and that paging needs a unique ordering ([pagination](https://www.postgresql.org/docs/current/queries-limit.html)).
- Collection distribution lists owned leaf Locations and direct quantity for one Edition; organizational rollups sum descendants, never imply a Holding exists directly in a parent. Search and filters join the already synchronized catalog, never call TCGdex on the inventory read path.

### Failure contract and readiness checks

- `400` handles malformed payloads/cursors; `422` handles invalid names or nonpositive quantities; `404` is uniform for unknown and cross-owner resources, including an Undo already physically deleted; `409` has stable codes for stale Holding/Location versions, insufficient quantity, invalid leaf or Deck target, sibling-name conflict, cycle, depth limit, an invalidated cursor, or incompatible Undo; `410` means an owned Undo record is still present but has expired; `503` handles transient database failure with the same idempotency key safe to retry. No error reveals another user's name, path, or quantity.
- Verify two-tab races, replayed commits after uncertain network results, Add versus Move, entire 25,000-Edition manifests, a failure midway through set-based transfer, empty/zero Holding transitions, root and sibling name uniqueness, cycle/depth and Deck child rejection, both stocked-leaf conversion paths, non-recursive deletion, multi-step Undo and expiry, derived Collection totals, cursor invalidation, and cross-user not-found behavior. Measure database bytes, Undo worst case, query plans/latency, and transaction duration against the 350 MB Neon prelaunch gate and hosting quotas. Upgrade the constrained component rather than adding a product-level bulk limit or weakening atomicity.
