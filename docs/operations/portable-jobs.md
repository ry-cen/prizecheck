# Portable operational jobs

The implementation selects no provider. A scheduler invokes independent commands in the application working directory, with secrets injected as environment variables. The backup and watchdog commands do not invoke one another. Install these schedules through the scheduler adapter chosen at deployment:

| Job                         | UTC schedule                           | Command                                                                                   |
| --------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------- |
| Daily logical backup        | Daily, 03:00                           | `.venv/bin/python scripts/operations_job.py backup`                                       |
| Independent backup watchdog | Hourly, minute15                       | `.venv/bin/python scripts/operations_job.py watchdog`                                     |
| Disposable recovery drill   | Monthly, first day04:00                | `.venv/bin/python scripts/operations_job.py restore --target tcg_recovery_monthly_YYYYMM` |
| Format Standing rule dates  | Daily, 00:05 UTC                       | `.venv/bin/python scripts/format_standing_job.py`                                         |
| Daily catalog refresh       | Daily, 04:00 UTC plus up to 30 minutes | `/opt/prizecheck-prod/bin/prizecheck-deploy.sh catalog-refresh`                           |
| TCGCSV price import         | Daily, first step of the refresh       | `python scripts/price_import_job.py [--force] [--rematch] \| --rebind-only`               |

The daily catalog refresh ([ADR 0018](../adr/0018-scheduled-catalog-change-check.md)) is run on production by the systemd timer `prizecheck-catalog-refresh.timer` (`deploy/host/`, installed by step 16 of the Oracle guide). It runs three steps in order: the TCGCSV price import, then the TCGdex change check (which pulls only when the card list changed), then the scanner index. A step that fails does not stop the later ones, except where noted below. The subcommand exits 0 when every step finished, and non-zero when the price import exited with anything but 0, the check failed or was killed, the index or the call that records its status failed, or a deploy began while it ran (the steps still to run are skipped and the log says so). It logs and exits 0 without running when another refresh holds its lock, a deploy holds the deploy lock at the start, or no release has been deployed yet. The check itself (`python -m app.catalog_refresh`) exits 0 for no change, a finished pull, a pull already running or a pause, 1 when the database is unreachable, 2 when the check failed, including when the live-derivation or marketplace-matching rule is not active (`CATALOG_RULES_INACTIVE`, no pull is started; the index still runs), and 4 when the pull it started failed (the index is skipped).

The TCGCSV price import ([ADR 0019](../adr/0019-tcgcsv-daily-prices.md)) downloads TCGCSV's daily Pokemon snapshot into PostgreSQL, binds each verified Edition to one price row and publishes the public price records. On the Oracle host it is the first step of `prizecheck-deploy.sh catalog-refresh`, which carries on to the catalog check and the scanner index whatever it returned and ends non-zero when the import exited with anything but 0. Run it by hand with `prizecheck-deploy.sh tool /app/scripts/price_import_job.py` (`--force` downloads again although TCGCSV's `last-updated.txt` is unchanged; `--rebind-only` downloads nothing and only rebinds, refreshes art and publishes; `--rematch` also re-evaluates the unverified promo Editions under the active matching rule). It exits 0 when it imported, found nothing new, or another run holds its lock; 1 when the database is unreachable; 2 when it failed; 3 when it was partial.

The scanner index job is a portable job that the catalog refresh runs on production after each check, except after a pull the check started that failed (ADR 0018, see above); elsewhere the operator runs it by hand after a catalog pull, in its own image, with `prizecheck-deploy.sh compose run --rm scanner-index` (add `--full` after a preprocessing change or to refresh the artwork). Inside the image the command is `python scripts/scanner_index_job.py [--full]`. It fetches each active printing's `low.webp` from `assets.tcgdex.net`, embeds it, and publishes the fingerprint file the scanner downloads. It exits 0 when the index was published or nothing was due, 1 when the database is unreachable, 2 when more than 2% of the printings failed (nothing is published; rerun later) or the embedder is unusable, and 3 when another run holds advisory lock 914711. A deploy pulls its image with the other services, so it is ready to run on the deployed commit.

The monthly target must be new; existing databases are never overwritten. Remove only that disposable target after recording the drill. Source connection is `DATABASE_URL`; restore administration uses `RESTORE_ADMIN_DATABASE_URL`. Scheduler installation, actual daily execution and remote durability need deployment evidence, rather than a code-level assertion.

The Format Standing job rebuilds the stored Format Standing of each Format whose rules changed on that day (a set becoming legal, a rotation, a ban); on other days it reads one row per Format and changes nothing. It exits 0 when every Format is current, 1 when the database is unreachable, and 3 when another rebuild held a Format's lock for longer than the wait (retry). A missed run is safe: the first Catalog read after a rule date rebuilds that Format itself and makes the read wait for the rebuild.

## Private object storage boundary

`scripts/private_backup_store.py` defines `PrivateBackupStore.put(key, source_path)`, `get(key, destination_path)`, `list(prefix)` and `delete(key)`. `put` must atomically replace the complete object; listings omit partial uploads. All objects are private. The filesystem adapter is selected by `BACKUP_PRIVATE_DIR` (root mode 0700, objects 0600). It refuses public-store overlap including the application's default public directory and an empty public-store setting.

To plug in remote private storage, set `BACKUP_STORE_FACTORY=installed_module:factory_function`. The no-argument factory obtains credentials from injected configuration and returns this protocol. It must enforce private bucket/container policy, encrypted transport, atomic complete-object replacement and the namespace scope. No recovery or API rewrite is needed. Authentication, object storage and scheduler provider identities never belong in manifests or logs.

A daily job holds a PostgreSQL advisory lock across backup/upload/retention, captures the logical snapshot with `recovery.py`, archives it, uploads it, reads it back and verifies SHA256 equality before atomically publishing `last-success.json`. Only then does it update owner status. Retention keeps the newest successful snapshot for each of the latest seven recorded UTC dates and four recorded ISO weeks; overlapping daily/weekly copies share one object. The currently referenced backup is always protected. All deletions happen after a verified new upload; unknown keys are untouched. Backup failures increment a sanitized counter and emit a bounded generic job result.

The independent watchdog reads persisted success metadata, checks age against 25 hours, serializes alert transitions in PostgreSQL and increments the incident counter once per stale period. A fresh backup resolves the period. Missing success metadata is an alert condition, while the panel labels the backup itself unverified. The panel includes the latest independent check timestamp so a stopped watchdog is visible.

## Alert delivery and quotas

The owner panel is always the alert fallback. Eligible email additionally requires `MAIL_SENDER_VERIFIED=true`, a verified owner recipient in the immutable owner binding, `MAIL_MODE=http`, `MAIL_RELAY_URL`, `MAIL_RELAY_TOKEN` and `MAIL_FROM`. This uses the same generic JSON envelope as the sign-in relay: `from`, `to`, `subject`, `text`. HTTPS is required; development permits HTTP on loopback only. Redirects are refused, requests time out after 5 seconds, and response bodies never become log data. The relay must honor the durable `Idempotency-Key` to prevent duplicates if a process dies after delivery but before the database acknowledgement. Failed deliveries remain pending for the next independent watchdog. Repeated stale checks do not create repeated incidents or send acknowledged alerts again.

Configured allowance adapters report measurements through:

```sh
.venv/bin/python scripts/operations_job.py quota --resource database_bytes --used 700000000 --allowance 1000000000
```

Resources are `database_bytes`, `storage_bytes`, `email_monthly`, `requests_monthly`, `runtime_ms`. The owner panel warns at 70% and marks measurements older than 25 hours unverified. Missing allowances are unverified. Supply measured values and contractual maxima; local synthetic inputs are not provider usage proof.

## Sanitized health

`GET /api/admin/operations` is signed-session owner-only. It exposes counts/timestamps for backup, restore, watchdog, catalog failures/reviews, private API requests/failures/authorization denials, sign-in requests/delivery counters, public projection failures/pending work, release failures and quotas. No emails, OTPs, tokens, Location names, card payloads or object keys appear. Private API trends are bounded hourly aggregates, kept 48 hours. Anonymous public projection routes skip the private-database metrics writer entirely.

Authentication and release adapters update only the fixed-name `operations_counter` vocabulary with an atomic increment. Delivery/failure counts remain unverified until an adapter records outcomes. The current mean response metric covers private API processing, not external network latency. This panel is operational evidence, not a substitute for release gates or a claim that a scheduler is installed.

## Local verification

2026-10-06/07 UTC, disposable PostgreSQL on port 55432 and local private object fixtures. `api/tests/test_operations.py` exercises owner authorization/privacy, real backup upload/verification, 35 daily snapshot objects reduced to seven daily/four weekly retention, job-driven disposable restore, injected missed schedule and deduplicated alert, controlled relay failure/retry/acknowledgement, and the 70% quota boundary. `web/tests/operations.spec.ts` covers the owner view's stale warning and allowance warning in the complete browser gate. The isolated recovery boundary suite remains in `tests/operations`.

Backup completion and watchdog marker evaluation share a PostgreSQL session advisory lock so an old observation cannot overwrite a newly completed backup. The separately scheduled processes keep independent lifetimes; marker publication and evaluation serialize. Expensive snapshot/upload work keeps a separate backup-run lock and does not block the independent watchdog. Backup and restore CLI failures, including adapter initialization and archive validation, increment their sanitized failure counters once whenever the private database remains reachable. Database outages cannot persist their own failure metrics.
