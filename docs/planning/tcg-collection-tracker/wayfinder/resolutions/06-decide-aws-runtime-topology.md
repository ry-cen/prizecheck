# Resolution — Decide the runtime, authentication, and hosting topology

**Historical decision:** Provider-specific topology is deferred by [ADR 0002](../../../../adr/0002-defer-deployment-provider-selection.md). The product and operational requirements below remain inputs; references to Workers, Neon, R2, Resend, GitHub Actions, and `workers.dev` describe the former candidate, not a current deployment commitment.

The owner confirmed this hosting and operations contract. The [relational-hosting comparison](11-compare-relational-hosting-options.md) supplies the provider rationale; the [catalog architecture](05-decide-catalog-architecture.md) supplies the manual pull and promotion contract.

The later owner decision in [ADR 0001](../../../../adr/0001-react-python-workers-auth-boundary.md) fixes the frontend as React/TypeScript/Vite and replaces the original TypeScript application API with a Python/FastAPI Worker plus an internal TypeScript Better Auth Worker. Workers Free remains the first tier to test; a measured CPU or quota failure requires optimization or a paid-tier decision before launch.

## Launch topology and environments

- Deploy React/TypeScript/Vite as Cloudflare static assets, a Python/FastAPI application Worker, and an internal TypeScript Better Auth Worker at one `workers.dev` origin. Try Cloudflare Workers Free first. Route same-origin auth traffic through a Service Binding and validate protected Python API requests with the internal auth service. Use Neon Free PostgreSQL, Better Auth email OTP, Resend Free as the first email adapter, Cloudflare R2 for public Published Deck projections and private logical backups, and included GitHub Actions minutes for CI, releases, Python catalog jobs, and backups.
- Keep local development and one production environment. Run PR tests in CI; no persistent staging deployment is required. Use standard PostgreSQL migrations, opaque application user IDs, HTTP contracts, and adapters for auth, email, jobs, object storage, and logs to preserve portability.
- The first deployment is owner-only. The owner must use the same email address for the initial application account and the Resend account, because Resend's test sender can deliver only to the Resend account address. Bind owner privileges to that application's immutable user ID by an explicit setup step, never to email text or first signup. All admin endpoints independently check that ID.
- The owner will register and verify a sending domain for Resend. Keep the website on `workers.dev` unless a later domain decision changes it. Open email-code registration to other users only after a real-recipient OTP delivery test succeeds through the verified sender. Domain registration does not block the owner-only first deployment, but it is a prerequisite for public signup. [Resend domain verification](https://resend.com/blog/new-domain-verification-experience); [Cloudflare's Resend setup](https://developers.cloudflare.com/workers/tutorials/send-emails-with-resend/).

## Authentication and email

- A valid email code creates an account for a new public user or signs in the existing user. Code requests return uniform responses to avoid account enumeration. Use a six-digit code, five-minute expiry, three wrong attempts before invalidation, rotation on resend, and hashed storage. Rate-limit sends with durable shared counters: one per normalized email per 60 seconds, five per email per rolling 24 hours, and 20 per trusted client IP per rolling hour. Read the IP from Cloudflare's trusted `CF-Connecting-IP` header. Cap all Resend sends at 90/day against the Free plan's 100/day allowance; expose a clear retry state when a limit is reached. Do not log codes, email addresses, session tokens, or raw provider responses. [Better Auth email OTP](https://better-auth.com/docs/plugins/email-otp); [rate limiting and trusted IP headers](https://better-auth.com/docs/concepts/rate-limit); [Resend Free limits](https://resend.com/pricing).
- Use a same-origin Secure, HttpOnly, SameSite=Lax cookie backed by a server-side session. The session lasts 30 days and rolls forward while active. Sign-out invalidates it. Protected API calls validate the session and derive ownership from the application user ID. Preserve the requested same-origin path across sign-in, rejecting external redirects. [Better Auth sessions](https://better-auth.com/docs/concepts/session-management).
- Starting an ordinary manual catalog pull uses the owner session. Approving a sensitive catalog identity override requires a fresh single-use email code bound to the owner and that approval action, even within a 30-day session. Backup restoration remains an out-of-app operator procedure.

## Catalog, public views, and backups

- Catalog synchronization has no schedule. The owner starts it in the frontend control panel; a GitHub Actions background job reports progress and result, as specified in the [catalog resolution](05-decide-catalog-architecture.md). A failed run leaves the current catalog active.
- Anonymous Published Deck reads use sanitized R2/edge projections rather than waking PostgreSQL for each view, as specified in the [public Deck resolution](09-decide-public-deck-contract.md).
- Run a daily logical PostgreSQL backup of user, authentication, Location, Holding, Deck, transfer, and publication data to a private R2 bucket. Exclude the rebuildable TCGdex catalog. Retain seven daily and four weekly copies. Document restoration and verify a restore into a disposable database at least monthly. Target a 24-hour recovery point. Keep private backup credentials and objects separate from public Deck projections.

## Observability and alerts

- Emit bounded structured events with request ID, route template, outcome, duration, and error code. Never log OTPs, email addresses, tokens, private Location names, or card payloads. Show the owner sign-in send/failure counts, authorization denials, API error/latency trends, catalog runs and review queue, backup age and restore-check result, R2 publication failures, and quota warnings. Health responses expose no private state. Workers Free Logs offers three-day retention within its included event limit. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/).
- Configure GitHub failed-workflow email notifications for eligible owner-triggered releases and scheduled backup/restore jobs. Show current job status in the owner panel. Catalog dispatch using a service credential may not send a GitHub notification to the owner; after the sending domain is verified, the application emails the owner about catalog failure. Before that, the owner checks the panel. [GitHub Actions notifications](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications); [notification recipients](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs).
- Run an hourly Cloudflare Cron watchdog independent of GitHub's backup schedule. It checks the last successful backup marker in private R2. If the marker is more than 25 hours old, mark the backup stale in the panel and email the owner once the sender domain is verified. Before verification, the panel warning is the fallback. This cron never starts catalog synchronization. An hourly check can detect the threshold up to one hour later: the alert catches a missed backup but cannot itself guarantee the 24-hour recovery point. GitHub may delay or drop scheduled runs, so a failed-workflow notification alone cannot detect a run that never started. [GitHub schedule behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows); [Cloudflare Cron limits](https://developers.cloudflare.com/workers/platform/limits/).

## Release and quota controls

- Production releases are manual after CI passes. Run Python and TypeScript checks, tests, builds, generated OpenAPI and schema compatibility checks. A credential-free release job verifies that the exact selected commit is on main and has successful required CI checks. Only its dependent job receives repository Actions secrets and deploys. Serialize production releases, apply backward-compatible migrations before the Workers, deploy internal auth before the Python API/assets, run a production smoke test, and keep prior compatible artifacts of both Workers for rollback without relying on reversing a destructive migration.
- Use a GitHub Free/private-compatible baseline: repository-level Actions secrets, manual `workflow_dispatch`, and only one maintainer with repository write access. These workflow gates do not substitute for branch protection against a writer who can change the workflow. Add branch or environment protection if the repository's visibility and plan permit it; the actual visibility/plan could not be verified in this session. [GitHub environment availability](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments); [protected branch availability](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches).
- Collect provider usage and application counters daily in the owner panel for Neon storage/compute/egress, Cloudflare Worker requests/logs, Resend daily/monthly sends, R2 Standard storage/Class A/Class B operations, and GitHub Actions minutes/storage. Provider dashboards or APIs are authoritative; show unavailable metrics as unverified and review those dashboards weekly and after an alert. Warn in the panel at 70% of any daily or monthly free allowance, and email the owner after the sender domain is verified. The owner investigates waste and upgrades the constrained component before a hard cap interrupts service. Preserve atomic transfers and backup retention when upgrading. Resend's 70% marks are 70/day and 2,100/month; Neon's 0.5 GB storage mark is 350 MB. A representative English catalog, indexes, authentication data, and 25,000-Holding fixture must fit under that Neon mark before launch, or the database plan must be upgraded. [Neon Free](https://neon.com/blog/neon-backend-is-ga); [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/); [R2 pricing](https://developers.cloudflare.com/r2/pricing/); [Resend pricing](https://resend.com/pricing); [GitHub included usage](https://docs.github.com/en/billing/reference/product-usage-included).
