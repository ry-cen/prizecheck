## Composition and edit lifecycle

Local entry provides `?decks=decks-empty|decks-failure|decks-slow|deck-stale`; `?owner=b` has distinct data with colliding Deck/Edition/Location ids. The Collection scenario remains independently selectable. Data is memory-only. Keys include game and owner. Deck summaries show the Deck List total as “N cards in this Deck”, with no target.

Index reads pause in the editor and refetch on return. An idle editor accepts a refreshed detail read. While list writes are in flight or pending, `acceptRead` and `acceptLocation` merge newer Location metadata while preserving pending list intent. Rename applies its returned name/version immediately, and older reads cannot replace them. Hashes carry section=decks, deck id and deckTab=deck|library. Back/Forward restores tab and Deck, with heading focus. Library uses the existing CatalogReader for exact Editions. Copy sheet uses neutral Dialog/Button primitives and per-Location holdings. List writes serialize per editor; clicks during a write coalesce into the next absolute-total batch at the returned revision. Transient failures retain payload/key. EDITION_UNAVAILABLE names no Edition, so every sent nonzero line absent from the baseline is a possible cause: a lone cause is dropped with its pending total (a re-click or zero queued after dispatch included), several are isolated and sent one at a time after the ordinary totals, and only one refused alone is dropped; there is no Retry for that intent. Unrelated sent or later queued changes survive, reload the list revision, and flush with a new key; a failed reload pauses only the kept work until a safe retry. Stale reload uses Pokémon wording. If every pending Edition still has its baseline quantity, its pending absolute total is retained for an explicit retry at the new revision and a new key. If any changed, pending totals are discarded and review is required. Unmount aborts and guards late completions, with no success toast. No collector-facing diagnostic IDs or source metadata appear.

WP3 correction: the Location dialog's alert describes only the current read of the Locations, never what happened to the collector's change or who changed the Locations. Whenever a read starts, manual or automatic, it says “Refreshing the list…”; it says “The list has been refreshed. Review it and try again.” only after a read has worked and something the collector saw changed, and “The list couldn't be refreshed. Try Reload and retry.” when the read failed. When a read works and nothing shown changed, the alert is cleared before the write is sent, so no read message shows while a write is in flight. A tree-change refusal drops the refused command and owes a fresh read: the dialog keeps Reload and retry, and a later new command (a click or Enter) reads the Locations first, whatever else the collector edits or chooses in between, until a write succeeds. Retrying a retained uncertain command (a send whose outcome is unknown) bypasses that read and reuses its original payload and key. A submit still needs a valid input: while the form is invalid (an unchanged name, or no parent chosen) the submit button is disabled and Enter does nothing, so no read happens until the input is valid again. If anything the collector last saw (the Location's path, its copies, the Locations inside it, or the destination) has changed, or the chosen destination can no longer be kept, the refreshed list is shown and nothing is sent; the next explicit submit reads again and, if nothing shown changed, sends with a fresh key. A reused key shows its own text, which asks the collector to use Reload and retry and does not say whether the change was applied; the next new command reads first and takes a new key (`web/src/games/riftbound/LocationWrites.tsx`, `submit` and the refusal catch; wording in `locationDestinations.ts`). The Deck rename and delete dialog names no source for a version change it cannot attribute: while an uncertain attempt is retained and the Deck's version moved, it says “This Deck changed. Retry checks your last change first.”, because the bump may be the attempt's own commit or a Deck List write; it says “renamed elsewhere” only when no attempt of its own can account for the change (`DecksView.tsx`, `DeckCommand`).

## Core arrival-coverage correction

Re-reading `migrations/core/000_baseline.sql:1143` (`deck_list_cover`), `:1218` (`deck_list_cover_holdings`) and the holding statement triggers at `:2813` and `:2817` established the inverse direction that the initial brief omitted: incoming Holdings can extend a Deck List. Departures never shrink it. With no Borrowed Copies, an arrival sets `max(listed, min(listed, held_before) + added)`. Filling an already-covered line leaves its revision unchanged; surplus cuts are preserved rather than listing every pre-existing physical copy. Insert and update transition-trigger phases each advance a growing Deck once, so a mixed upsert can advance it twice. This is generic core storage behavior, not a Riftbound construction count or target.

`local/deckListFixtures.ts` shares headers through the owner-scoped Collection store identity. Collection Add, Move and ordinary Inventory Undo invoke the coverage rule. Replay applies no arrival twice. A retained owned Edition may therefore acquire a new line through a physical Move, even though an explicit new Deck List line is refused by the active-catalog check. Inventory Undo restores Holdings through a single upsert (`api/app/core/inventory/moves.py:409`); Put away's returns-as-surplus exception remains outside this slice. No Deck List Undo UI or new Undo record is added.

Inventory revision changes refetch Deck reads without changing the same-Deck read key, so an idle editor updates ownership after the existing global Inventory Undo action. Pending list intent stays owned by its write queue. Unit cases cover mixed insert/update arrivals, replay and owner isolation, covered lines, surplus cuts, retained Editions and Inventory Undo. The browser journey moves an actual Collection copy into an empty Deck, then verifies its In this Deck count and the ownership refresh after Undo.

Copy sheets and command dialogs close when history changes the editor tab. Removing a line at zero clears its opener state and focuses the Deck heading, preserving all Holdings. Browser coverage checks Back/Forward with a sheet open and removal of the retained line without a phantom sheet reopening.


Extra repair: core `api/app/games/pokemon/decks/routes.py:268-278` refuses the whole batch with EDITION_UNAVAILABLE and no Edition id, so the refusal cannot say which line caused it. Every sent line with a nonzero quantity whose Edition was not on the baseline list is a possible cause, whatever the collector has queued for it since (a second click or a removal while the batch was in flight does not clear it). With exactly one such candidate it is certainly unavailable: its pending total is dropped, including any re-click or zero queued after dispatch. With several, candidates whose pending total is now 0 are dropped as no-ops and the rest are isolated with their current totals. Non-candidate totals flush first, then each isolated candidate is sent alone with a fresh key at the current revision. One refused alone is dropped with its pending re-clicks; one accepted alone stays applied. Both refusal reload sites compare kept Editions against the pre-reload intent baseline, drop only changed Editions and pause for review; Retry applies only unchanged kept totals. When that review also follows a refusal, the message names both causes. The STALE path retains its existing all-or-review behavior explicitly and clears its isolation marks with the totals. Open Rename drafts and focus survive newer Locations; submit uses the current version. A request in flight is not aborted by a version change: a result whose Location version equals the current version is the collector's own success, and only an unattributable change shows "renamed elsewhere", with the draft kept, a fresh key on resubmit and focus returned to the name field (also after a stale-Location reload). Delete tracks the current confirmation name and disables mismatched text. Rename and Delete classify a failed command. A definitive refusal is exactly one of STALE_LOCATION, INVALID_LOCATION_NAME, LOCATION_NAME_CONFLICT, LOCATION_NAME_CONFIRMATION_MISMATCH, DECK_NOT_FOUND, IDEMPOTENCY_KEY_REUSED, UNSORTED_UNAVAILABLE or QUANTITY_OVERFLOW, and it clears the attempt. The last two are raised by Deck deletion inside its transaction, after the replay check (core `api/app/deck_deletion.py:58` and `:105`, replay at `:73`). QUANTITY_OVERFLOW can follow writes made earlier in that same transaction, such as the Unsorted rename or insert at `:55` and the borrowed-copy move, but the transaction rolls them all back, so a refused Delete commits no change and its Retry could never succeed. The fixture `deleteDeck` in `local/deckFixtures.ts` raises both before mutating and after its replay check in `command`. It is not enough for a failure to be a DeckError: any other failure (a network error, a non-DeckError, a lost response, an unlisted code) is uncertain: the dialog keeps the exact name or confirmation text, the version it was first submitted against and its idempotency key, says "Your last change may not have been saved. Try again to check safely.", and never claims a rename elsewhere, and moves focus to Retry. A new attempt drops the previous attempt's notes; "This Deck changed. Retry checks your last change first." appears only when the version moved during the attempt; it names no source, since the move may be the attempt's own commit. A background version change does not clear it. Retry resends the same payload, version and key, so the fixture replay (and core's) returns the stored result and the dialog finishes as the collector's own success with one mutation. Delete shares the component and so the rule, even when the Deck's name has changed in the meantime.
