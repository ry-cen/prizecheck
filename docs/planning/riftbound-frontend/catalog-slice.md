# Riftbound local Catalog (#660)

This is a fixture-backed frontend slice, not a live or deployed product. Start it with `npm run dev:riftbound`, then open `http://127.0.0.1:5173/src/games/riftbound/local/index.html`. It requires only the worktree's Node dependencies; no auth, API or database server. Search for `001`, open either Edition, close with Escape, use Back/Forward, clear search, and use Next page to exercise the slice.

The HTML lives under the game’s local directory and is absent from the production Rollup inputs. The Pokémon entry, routes, menus, generated clients and preference files are unchanged. There is no shared-to-Riftbound import or new allow-list edge. The production bundle check rejects Riftbound modules even in private lazy chunks. The local HTML explicitly composes the synthetic reader; a failed request never switches readers or supplies fixtures as fallback.

## Adapter and fixtures

`web/src/games/riftbound/catalog.ts` owns the narrow `CatalogReader` contract: sets, paged Edition listing and Edition detail, each taking an AbortSignal. The query supports case-insensitive name/collector-number substring search, one set, one supplied domain and one supplied card type. Pages contain eight Editions. An Edition carries a distinct Printing identity, set, collector number, supplied finish, optional art and orientation; no gameplay or format rules are inferred. All names and data are synthetic and make no claim about the actual card pool. Fury/Calm and Unit/Spell/Battlefield are the only facet values supplied by this fixture contract.

Fourteen Editions include two finishes of the same Printing, another Printing of the same named card in another set, missing art, and original inline landscape Battlefield art. Images use containment. Fixtures make no network requests. `?scenario=empty`, `?scenario=failure`, `?scenario=detail-failure` and `?scenario=slow` expose empty catalog, fail-once list/detail reads with Retry, and delayed initial reads. No matches has its own clear-filters action.

The view uses the shared PageHeader, SearchField, Chip, PickerChip, ScrollArea, Button and CardPopup/Dialog. Tile frame and names-line tokens come from the game-neutral CopyTile styles. Pokémon is the visual/interaction baseline: top navigation on desktop, header plus bottom Catalog tab on phones, one search field and horizontally scrolling filter row, Edition tiles, centered detail on desktop and bottom sheet on phones. Game-specific differences are supplied facets, finish labels and landscape art. Unavailable inventory, deck, social, scanner, owner and import/export actions are absent. Explicit numbered paging is used for this narrow read contract.

## State ownership and integration gap

All list addresses use the `#riftbound:` namespace; listing keys include `riftbound` and every query field. Detail and React row keys are game-prefixed too. There is no global read cache, storage or shared kept-page state. List state stays mounted when leaving for the local home; no Pokémon preference key/value is read or written. Abort plus effect-lifetime guards reject stale success/failure, including adapters that ignore abort; keyed rendering suppresses previous selections before effects run. The shared modal restores opener focus on dismissal and history traversal.

#650 supplies persistence and shared reader proof, not a mounted read API. #661 must define and generate the actual game-specific read client and explicitly compose a production reader after routing/contract decisions. It must map only supported facets and supplied finishes, preserve cancellation/error semantics and remove the local-only bundle restriction only with an authorized production composition. This slice chooses no public URL, auth strategy, sync mechanism or live data source.
