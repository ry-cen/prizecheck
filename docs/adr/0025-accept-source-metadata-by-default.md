# Accept rule-verified source metadata by default

Status: Accepted, at the owner's request on 2026-11-11. Refines ADR 0007.

The owner should review current conflicts, rather than obsolete source evidence. During import, pending reconciliation reviews become `stale` when their kind is no longer raised, or `superseded` when a newer review key carries the same kind (including reviews inserted in that import). A conflict raised again under an automatically closed review's own key reopens the same row. Automatically closed rows never count as owner decisions. `retained`, `confirmed` and `corrected` decisions remain unchanged. A current `source_match` still requires manual confirmation; equality of match fields is not independent physical evidence.

A verified Card Edition with a matching-rule Marketplace Mapping follows a changed candidate only when the active rule verifies it again, correspondence is `source_candidate`, its fingerprint was never rejected, no other target holds its product/quote variant, and no open marketplace report concerns that exact Edition. This default acceptance applies only to `candidate_changed`; owner mappings, Catalog Overrides, real conflicts and all Live import behavior remain protected. Variant descriptor differences, including thirdParty and unknown facets, are not normalized away. A changed rule mapping is quarantined as before when no matching rule is active or a collector's report on that Edition is open, and it stays quarantined after the report closes or a rule is activated. A changed V5 card-level TCGplayer ID is source evidence like a variant's product ID: the active rule may re-verify the Edition from it. When the change leaves the active rule nothing to verify, as when a card-level ID that was the only product evidence is removed, the Edition is quarantined.

Imports never lift an existing quarantine or suspension. The owner may run `python scripts/settle_review_backlog.py --owner USER_ID` to print a read-only plan, then add `--apply` to settle it. Both modes refuse while the catalog runner is busy. The command rechecks current evidence under the correction locks and skips changed targets. It releases rule mappings under the same policy, physical-conflict Editions only after identity reviews clear (maintainer mappings additionally require unchanged accepted evidence and no collision), and Live identity-review suspensions only with unchanged accepted export evidence and a successful reviewed refresh inside a savepoint. Other reasons, rejected candidates and open reports remain manual. This includes a rejected Live export fingerprint even when its projection matches accepted evidence. Dry-run planning treats only the obsolete reviews it would close as non-contesting; apply commits those closures and re-plans metadata before releasing dependents, so an unchanged second run has no additional work.

Every automatic closure, reopening, acceptance and release appends before/after evidence to `catalog_auto_settlement`. Import events have no actor; command events identify the owner. Human metadata decision history is unchanged. Repeated source flapping can close and reopen evidence repeatedly, with one audit event for each transition.

The settlement steps this decision adds never lock the inventory-owner row and never wait for a lock while they hold one an existing request could need. This covers the added steps only, not the import as a whole. The import already waited for the clock while holding `catalog_state` before this decision, and still does. That wait can join a cycle with an owner's metadata decision (which holds the clock, then needs the owner row for its decision record) and the same owner's inventory request (which holds the owner row, then needs `catalog_state`); PostgreSQL then aborts one of the three. This decision neither adds to that cycle nor removes it; reordering the import's locks is separate work. Each automated transaction waits only for its first lock: the import's `catalog_state` and clock (as before), a command review batch's `catalog_state`, or a command target's clock. A command review batch then takes the clock row and its review rows `NOWAIT`. Before an automated metadata transition, automation locks the Edition or Printing that report foreign keys reference `FOR UPDATE NOWAIT` and re-checks reports in a fresh READ COMMITTED statement. Metadata rows and Live peers are waited for only because every writer of them holds the clock first. Command audit rows name the owner in `actor_id` without a foreign key, because collectors' inventory requests lock that row before `catalog_state`; the command checks owner access before planning and before applying. A busy lock, lock timeout or deadlock rolls back that batch or target, which is printed and counted as skipped. When an Edition is busy at import (for example, while a report is filed or a holding added), it is quarantined as before, without an acceptance audit. The owner-run command or a review releases it once the guards allow.
